# FINOS CDM バージョニング体系 & 互換性ガイドライン

FINOS Common Domain Model (CDM) は、金融業界全体（デリバティブ、レポ、証券貸借、規制報告など）で共有される共通データ・業務ロジック標準として、厳格な **Semantic Versioning 2.0.0 (SemVer)** を採用してバージョン管理を行っています。

本ドキュメントでは、メジャーバージョンおよびマイナーバージョンのインクリメント基準、変更種別の定義、そして同一メジャーバージョン内における後方互換性（Backward Compatibility）の保証範囲と境界について解説します。

---

## 1. CDM バージョン番号の基本構造

CDM のリリースバージョンは `MAJOR.MINOR.PATCH`（例: `6.24.0`, `7.1.0`）という 3 つの数字で表されます。

```text
       MAJOR . MINOR . PATCH  [-DEV.x]
         │       │       │        │
         │       │       │        └── プレリリース識別子（開発版・コミュニティ PoC）
         │       │       └─────────── 後方互換性のあるバグ修正・ドキュメント修正
         │       └─────────────────── 後方互換性のある新機能追加・属性追加
         └─────────────────────────── 後方互換性のない破壊的変更（スキーマ・型の再構築）
```

また、開発サイクル中には以下の 2 種類のリリーストレインが並行管理されます：
- **Production Version（本番安定版）**: `MAJOR.MINOR.PATCH`（例: `6.24.0`）。破壊的変更は一切含まず、後方互換性が厳密に維持される。
- **Development Version（開発プレリリース版）**: `MAJOR.0.0-DEV.x`。次期メジャーバージョン向けに破壊的変更や大幅な機能改善をコミュニティで迅速にプロトタイピング・合意するためのビルド。

## 2. バージョンごとのインクリメント基準

### 2.1 メジャーバージョン（MAJOR: `6`, `7` など）のインクリメント
**「後方互換性のない破壊的変更（Backward-Incompatible / Breaking Changes）」**が導入された場合にインクリメントされます。

既存のモデル利用者が、自社のシステム実装やデータ変換パイプラインの修正を行わずにそのまま新バージョンへアップグレードできない変更がこれに該当します。

#### 破壊的変更（メジャーアップグレードが必要な変更）の具体例：
1. **要素の削除（Removal）**:
   - 既存のデータ型（`type`）、属性（attribute）、関数（`func`）、列挙型（`enum`）、列挙値の削除。
2. **要素の名称変更（Renaming）**:
   - 型名、属性名、Enum 値、関数名のリネーム（旧名での参照が不可能になるため）。
3. **データ型の変更（Type Alteration）**:
   - 属性のデータ型を別の型に変更（例: `string` から `LegalEntity` への変更、親型の差し替え）。
4. **カーディナリティ・バリデーションの厳格化**:
   - オプショナル属性を必須属性に変更（例: `[0..1]` から `[1..1]`、`[0..*]` から `[1..*]` への変更）。
   - 新たなバリデーションルールや `condition` の追加により、従来「有効（Valid）」として受け入れられていた既存インスタンスが無効（Invalid）になる場合。
5. **関数のインターフェース変更**:
   - 関数の引数（`inputs`）の型変更、必須引数の追加、戻り値の型変更。
6. **アーキテクチャの大規模リファクタリング**:
   - ISDA CDM から FINOS CDM への移管に伴うモジュール再編、取引ライフサイクルイベント構造の再設計、プロダクト Payout 階層の統合など。

---

### 2.2 真ん中のバージョン（MINOR: `6.24` の `24`、`7.1` の `1` など）のインクリメント
**「後方互換性を完全に維持した機能追加・機能拡張（Backward-Compatible Feature Additions）」**が行われた場合にインクリメントされます。

既存のシステムや保存されたデータに一切の変更を強制せず、純粋に新しい機能やモデル要素が追加される場合です。

#### マイナーバージョンで許容される変更の具体例：
1. **新しい型の追加**:
   - 新しいデータ型（`type`）、列挙型（`enum`）、インターフェースの追加。
2. **既存型へのオプショナル属性の追加**:
   - 既存の型に対して、カーディナリティが `(0..1)` または `(0..*)` の**任意属性**を追加（既存データにその属性が存在しなくても検証エラーにならない）。
3. **列挙型（Enum）への選択肢の追加**:
   - 既存の `enum` に新しい列挙値（Value）を追加（※新規概念のサポート）。
4. **新しい関数・計算ロジックの追加**:
   - 新しいビジネス計算関数、参照金利取得関数、適格性判定関数（`Qualify_`）の追加。
5. **新しい商品・イベントのサポート**:
   - 新たなデリバティブ商品種別（例: 特定のコモディティスワップ）や新しいコーポレートアクションイベントの追加。
6. **規制報告マッピング（DRR等）の拡張**:
   - 新しい法域（CFTC、EMIR、JFSA、ASIC等）向けのルールセットやマッピング定義の追加。

---

### 2.3 パッチバージョン（PATCH: `6.24.1` の `1` など）のインクリメント
**「後方互換性のあるバグ修正（Backward-Compatible Bug Fixes）」**や軽微な修正が行われた場合にインクリメントされます。

- 条件式（`condition`）のロジックバグ修正（本来意図された仕様への整合化）。
- ドキュメント、定義記述（definition）、アノテーションの誤字・脱字の修正。
- Rosetta DSL コンパイラや Java コード生成器の不具合修正に伴う内部調整。

---

## 3. 同一メジャーバージョン内における互換性の保証範囲

メジャーバージョンが同じである限り（例: `6.0.0` から `6.24.0` まで）、CDM は以下の互換性を保証します。

### 3.1 データ互換性（インスタンスの後方互換性）
- **過去データの妥当性保証**:
  古いマイナーバージョン（例: CDM 6.0）で作成・シリアライズされた有効な JSON/XML メッセージ（`TradeState` や `BusinessEvent` など）は、同一メジャー内の最新マイナーバージョン（例: CDM 6.24）のスキーマやバリデーションにかけても、**100% 有効（Valid）**として検証を通過します。
- **理由**:
  既存のフィールドは削除・改名されず、必須化もされないため、既存のデータ構造が壊れることはありません。

### 3.2 ソースコード & API 互換性（コンパイル・バインディング互換性）
- **既存 API 呼び出しの非破壊**:
  Rosetta DSL から生成される Java クラスやインターフェースにおいて、既存の型名、ゲッター/セッター、ビルダーメソッドのシグネチャは維持されます。
- **ライブラリ差し替え**:
  CDM 6.0 を前提に書かれた業務アプリケーションコードは、ライブラリの依存関係を CDM 6.24 に更新しても、再コンパイルが通り、そのまま動作します。

## 4. 互換性の境界と実装上の注意点

同一メジャーバージョン内であっても、システム実装上で留意すべき「境界」が存在します。

| 観点 | 保証状況 | 注意点・対策 |
|---|---|---|
| **後方互換性 (Backward)** | **完全保証** | 古いバージョンで作られたデータ・コードは新しいバージョンで問題なく動作する。 |
| **前方互換性 (Forward)** | **非保証** | 新しいマイナーバージョン（例: 6.24）で新たに追加されたフィールドを含むデータを、古いバージョン（例: 6.0）のパーサーで読み込む場合、パーサー設定（例: Jackson の `FAIL_ON_UNKNOWN_PROPERTIES`）によっては未知のフィールドとしてエラーになる可能性がある。 |
| **Enum の網羅性チェック** | **実装依存** | 既存の `enum` に新しい値が追加された場合、Java コードで `switch-case` の網羅分岐（exhaustive switch）を記述していると、未知の Enum 値を受信した際に `default` 句のハンドリングや例外処理が必要になる。 |
| **Pre-release (DEV版)** | **保証外** | `-DEV` タグが付いたプレリリースビルド同士の間では破壊的変更が許可されているため、本番運用には必ず正式リリース版（Production Version）を使用する。 |

---

## 5. まとめ・対応マトリクス

| バージョン種別 | 変更内容の性質 | 既存データの互換性 | 既存コードの互換性 | バージョン表記例 |
|---|---|---|---|---|
| **MAJOR** | 破壊的変更（型・属性の削除/改名/必須化、再設計） | ❌ 変換・修正が必要 | ❌ コード修正が必要 | `6.0.0` → `7.0.0` |
| **MINOR** | 後方互換な機能追加（オプショナル属性、新規型、新規関数） | ⭕ 完全維持 | ⭕ 完全維持 | `6.23.0` → `6.24.0` |
| **PATCH** | 後方互換なバグ修正（条件式修正、誤記訂正） | ⭕ 完全維持 | ⭕ 完全維持 | `6.24.0` → `6.24.1` |
| **DEV** | 開発プレリリース（次期メジャー向け試作） | ⚠️ 保証なし | ⚠️ 保証なし | `7.0.0-DEV.12` |
